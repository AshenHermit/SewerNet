# Адаптивный web-клиент SewerNet

Дата: 2026-11-18
Статус: дизайн утверждён пользователем 2026-11-18; независимый builder check выполнен ранее (подтверждено пользователем). Следующий согласованный шаг — подготовить план реализации через `writing-plans`, затем согласовать план до изменения product code.
Ветка: `feat/responsive-design`.

## 1. Намерение

Реализовать адаптивный дизайн существующего web-клиента и основу для дальнейших экранов. На телефоне ориентир — структура мобильного Telegram из трёх предоставленных пользователем скриншотов: список чатов, отдельная переписка, отдельные настройки, плавающая нижняя навигация вне переписки.

Это не копирование Telegram целиком. Сохраняются темы, UI kits, Matrix-интеграция и текущие функции SewerNet.

Пользователь выбрал единый адаптивный каркас с важным уточнением: некоторые компоненты должны иметь разные мобильные и desktop-представления. Нельзя превращать общий каркас в ограничение, заставляющее сжимать любой desktop layout для телефона.

## 2. Объём и ограничения

### Цели

- Адаптировать комнаты, переписку, настройки, вход и статусные экраны.
- На узком экране показывать один основной раздел; на широком сохранить три колонки.
- Общая навигационная модель и состояние, без отдельного мобильного приложения.
- Общие правила ширины, safe-area, высоты viewport, прокрутки и зон нажатия.
- Поддержать как CSS-адаптацию одного компонента, так и замену его представления.
- Документировать контракт для будущих экранов и новых UI kits.
- Проверить поведение на границе режимов, а не только несколько удачных размеров.

### Не входит

Контакты, профиль, папки, архив, звонки, новые Matrix-функции, обои Telegram, платформенные status bar, swipe-навигация, сложная анимация переходов, Tauri и лендинг. Не добавляются отдельные URL для комнат/настроек или управление browser history. В этом этапе работает явная кнопка «назад» внутри приложения. Сохранение черновиков после перезагрузки и полноценное хранение черновиков для каждой комнаты — отдельные задачи.

### Недопустимые результаты

- Дублирование Matrix-клиента, SDK-хуков или бизнес-логики ради мобильного UI.
- Сброс текущего черновика, поиска, выбранной комнаты или темы при изменении ширины.
- Две активные копии формы/навигации с повторяющимися ID и focusable-элементами.
- Стили и оформительские HTML-элементы в `apps/web`.
- Недоступный ввод под клавиатурой, обрезанные настройки, нижняя навигация поверх последних строк списка.
- Определение телефона по user-agent или обязательное одинаковое дерево разметки для всех представлений.

## 3. Рассмотренные подходы

1. **Общий CSS-first каркас с адаптивными слотами — выбран.** Раскладка и большая часть изменений задаются CSS в `libs/ui`. Общая логика передаёт семантическое состояние через props. Там, где различие не решается разумной CSS-адаптацией, слот переключает stateless-представление. Меньше дублирования, единое состояние, возможность отходить от desktop-композиции.
2. **Отдельные mobile/desktop композиции.** Больше свободы на уровне всего экрана, но две независимые композиции повышают стоимость поддержки, проверки и сохранения состояния. Пользователь предпочёл общий каркас, сохранив возможность локальной замены компонентов.

Работа существенная: меняется каркас и контракт UI, а не только набор CSS-классов. Поэтому нужен полный дизайн и отдельный план реализации.

## 4. Что существует сейчас

- `apps/web/src/app/screens/chat-screen.tsx` передаёт `Rail`, `RoomList`, `ChatView` как произвольные children в `ProxyChatScreen`.
- `libs/ui/src/lib/kits/shadcn/chat-screen.tsx` — горизонтальный flex без переключения панелей.
- `ChatViewHeader` уже содержит кнопку «назад» с `md:hidden`, но остальная раскладка с ней не согласована.
- `apps/web/src/app/stores/chat-store.ts` хранит только `activeRoomId` и ошибку. Данные комнат и таймлайна находятся в SDK; клиент — singleton.
- Черновик и отправка находятся в `ChatView`, поиск — в `RoomList`. Эти контроллеры нельзя перемонтировать из-за изменения ширины или перехода к настройкам.
- Настройки сейчас открываются из локального состояния `Rail`; UI использует `absolute bottom-16 left-16 w-72`, без адаптивного контейнера.
- `ChatView` и `RoomList` содержат остаточные `className` и HTML-разметку вопреки `ARCHITECTURE.md`; затрагиваемую разметку нужно перенести в UI kit.
- `libs/ui/src/styles.css` и `apps/web/src/styles.css` отдельно задают одинаковую палитру. Общие адаптивные правила должны подключаться из одного источника в приложение и Storybook; полной переработки темы не требуется.
- Storybook имеет общий padding и centered layout; полноэкранным историям нужен отдельный режим без этих ограничений.

## 5. Режимы и геометрия

Предложенная агентом граница: `48rem` (768 CSS px при стандартном корневом размере). Она прозвучала при выборе подхода; точное значение остаётся явным проектным решением, которое пользователь может скорректировать при согласовании документа.

- **Compact:** ширина меньше `48rem`; одна основная панель.
- **Wide:** ширина от `48rem`, включая точную границу; rail + комнаты + переписка.
- Отдельный tablet-режим пока не вводится. Используется доступная ширина, а не тип устройства; узкое окно desktop работает как compact.

Порог — единый источник в `libs/ui`. CSS и механизм выбора заменяемых представлений обязаны использовать одно значение, включая Storybook. Новые компоненты не вводят свои `md:hidden` или независимые числовые проверки для переключения основного режима.

Ширины wide-панелей, отступы, размер нижней навигации и минимальный touch-target оформляются именованными layout tokens. Точные размеры, кроме порога и минимальной зоны нажатия 44×44 CSS px в compact, оставлены исполнителю. При 768 px rail и список должны оставлять переписке полезную ширину; чат всегда имеет `min-width: 0`.

Для внутренней компоновки компонентов предпочтительны flex/grid и container queries: узкий чат внутри wide-каркаса тоже обязан корректно переносить содержимое.

## 6. Контракты и гибкость UI

### Адаптивный каркас

`ProxyChatScreen` становится компонентом с именованными слотами: rail, комнаты, переписка, настройки, нижняя навигация. Семантическое состояние активного раздела приходит через props; расположение, видимость и оформление принадлежат kit. Точные имена props выбирает исполнитель, но контракт не должен опираться на порядок children или CSS-селекторы по позиции элемента.

Контроллеры комнат и переписки остаются стабильными React-компонентами. Каркас скрывает неактивные основные панели через CSS/семантическую видимость, не удаляя контроллеры из дерева. Скрытые панели не участвуют в layout, tab order и accessibility tree. Не использовать только opacity, отрицательный translate или `aria-hidden` поверх всё ещё доступных контролов.

### Замена представления

В `libs/ui` добавляется переиспользуемый proxy-контракт адаптивного слота/представления, зарегистрированный в `UiKit`, с вариантами compact и wide и общим fallback. Он действительно монтирует только выбранное представление; это не двойной рендер с сокрытием одной копии. Без специального варианта используется общий компонент.

Его ответственность — выбор UI, не хранение данных приложения. Состояние, которое должно пережить замену (черновик, поиск, выбранные значения, отправка), хранится выше слота в стабильном контроллере приложения и передаётся обеим реализациям через одинаковый контракт. Локальное эфемерное состояние презентационного компонента может сбрасываться; это явно описывается в README.

Механизм подписки на режим — внутренний для UI-библиотеки, корректно очищает подписки, имеет детерминированный начальный snapshot и безопасен без `window`. Приложение не добавляет собственные `matchMedia`, resize listeners или проверки ширины. Конкретный способ связать CSS-токен с подпиской оставлен исполнителю; тест должен предотвращать расхождение режимов.

Первый реальный пример разного представления — навигация: desktop rail и compact bottom bar с общими действиями. Второй — контейнер настроек: desktop dialog/popover и compact экран с общей формой. Это должно показать, что замена поддерживается на практике, а не только описана в документации.

### Остальные proxy-компоненты

Добавляются необходимые semantic-компоненты для заголовка списка комнат, нижней навигации, пустой переписки и прокручиваемого списка комнат. Они включаются в `UiKit`, реализации shadcn и публичные proxy-exports. Переводы и действия остаются в `apps/web`; UI принимает готовые строки/nodes и callbacks.

## 7. Навигация и состояние

Разделы: `rooms`, `chat`, `settings`. Это неперсистентное UI-состояние, независимое от `activeRoomId` и ширины экрана; тема и язык используют существующий persist.

- Начальное состояние после входа — `rooms`; выбранной комнаты может не быть.
- Выбор комнаты устанавливает `activeRoomId` и раздел `chat`.
- «Назад» из переписки переводит в `rooms`, но **не очищает выбранную комнату**. Так переход к списку не разрушает контекст и wide-режим может продолжить показывать выбранную переписку.
- Нижняя кнопка «Чаты» показывает список комнат, «Настройки» — настройки.
- «Закрыть/назад» из настроек возвращает к списку. В wide закрывается только overlay; выбранная переписка остаётся видимой.
- При переходе wide → compact показывается сохранённый раздел; если открыт `chat`, но нет `activeRoomId`, используется `rooms`.
- При переходе compact → wide снова видны три колонки. Открытые настройки становятся overlay. Ни resize, ни замена презентации не меняют выбор комнаты или Matrix-сессию.
- Выход доступен на обеих раскладках. В compact — действие в настройках; в wide сохраняется rail. Существующий безопасный порядок очистки credentials перед `logoutCurrent()` сохраняется.
- Изменение режима не вызывает новую отправку, сброс ошибки, повторный read receipt или переподключение SDK.

Модель переходов и состояние открытия настроек поднимаются из `Rail` в общий контроллер/публичные действия UI-store. Точное распределение между `ChatScreen` и store оставлено исполнителю; состояние не должно зависеть от того, какое навигационное представление сейчас смонтировано.

## 8. Вид экранов

### Compact: комнаты

Верхний заголовок SewerNet, затем поиск и полноширинный список с аватарами, названиями и превью. Палитра, шрифт и акцент — текущая тема. Плавающая компактная нижняя панель содержит только «Чаты» и «Настройки», обозначает активный раздел. Нижний отступ списка учитывает панель, зазор и safe-area: последний элемент доступен полностью.

Не добавляются декоративные кнопки создания чата, папки и отсутствующие разделы. Начертания и радиусы могут напоминать референс, но не фиксируются в обход настройки темы.

### Compact: переписка

Полноширинный экран без rail, списка комнат и нижних вкладок. Шапка с доступной кнопкой «назад», аватаром, названием и текущей информацией о комнате. Длинные название/ID и E2EE badge не выталкивают кнопки за экран.

Шапка и composer не сжимаются; скроллится таймлайн. Поле ввода и действия остаются доступны при коротком viewport. Длинные строки, URL и sender IDs переносятся; широкие pre/table/media, если их рендерит текущий компонент, ограничиваются шириной своей панели или прокручиваются внутри содержимого, не создавая горизонтальный скролл страницы. Не подменять текущий рендерер сообщений и не расширять функциональность Markdown/media ради адаптива.

### Compact: настройки

Отдельная панель с заголовком и общей существующей формой внешнего вида/языка; нижние вкладки остаются видимыми. Содержимое скроллится независимо и не обрезается на малой высоте. Добавляется доступный выход; не имитируются отсутствующие настройки Telegram. Управление цветовой схемой заменяет необходимость отдельной mobile-кнопки быстрого переключения темы.

### Wide

Rail слева, ограниченная по ширине колонка комнат, переписка занимает остаток. Настройки — ограниченный viewport доступный dialog/popover с прокручиваемым содержимым, Escape, переносом фокуса внутрь и возвратом фокуса к trigger после закрытия. Если выбран модальный dialog, он должен иметь соответствующую семантику, backdrop и focus trap; не смешивать семантику modal с немодальным поведением.

### Вход и статусы

Карточки ограничиваются шириной viewport. При малой высоте весь экран допускает вертикальную прокрутку вместо вертикального центрирования с обрезанием верхней части. Поля и кнопки доступны при клавиатуре; длинные ошибки не расширяют страницу.

## 9. Viewport, прокрутка, доступность

- Общие CSS-правила в UI-библиотеке подключаются и приложением, и Storybook; приложение сохраняет только bootstrap/imports, а не второй комплект responsive styles.
- Full-screen shell использует динамическую высоту viewport с разумным fallback. `min-height: 0` и `min-width: 0` выставляются по всей необходимой flex/grid-цепочке.
- Учитываются `env(safe-area-inset-*)`; viewport meta допускает вырезы экрана и, где поддерживается, resize контента при клавиатуре. Не запрещать пользовательский zoom.
- Поведение клавиатуры проверяется отдельно: `100dvh` сам по себе не считается доказательством, что iOS/Android keyboard не закрывает composer. Дополнительная работа с visual viewport допустима только при необходимости, в общем UI-слое, без UA-sniffing.
- Основная прокрутка — внутри комнаты/списка/настроек; у shell нет случайного второго вертикального скролла. Вход и статусы могут скроллиться целиком.
- Навигационные действия имеют переведённые accessible names, видимый keyboard focus и активное состояние (`aria-current` или корректная семантика выбранного раздела).
- При смене раздела фокус не остаётся внутри скрытой панели: переход в переписку/настройки переносит фокус на подходящий заголовок или контроль; возврат к списку — на выбранную комнату либо заголовок списка. Закрытие wide-настроек возвращает фокус на trigger.
- При resize перенос фокуса нужен лишь если текущий элемент стал скрыт или заменён; не забирать фокус у поля ввода без причины. Смена режима не должна терять значение поля.
- Минимальные зоны нажатия compact — 44×44 CSS px, включая назад, вкладки, вложение, отправку, закрытие и основные кнопки настроек. Mobile-поля не провоцируют нежелательный iOS auto-zoom (обычно размер текста не меньше 16 px).

## 10. Проверки и критерии приёмки

### Автоматические

- Unit-тесты переходов: выбор комнаты, назад без очистки выбора, вкладки, закрытие настроек, fallback при отсутствии комнаты, доступность logout.
- UI/proxy-тесты контрактов именованных слотов и делегирования активному kit.
- Тест адаптивной замены: compact/wide/fallback, только одна активная реализация, изменение media query, cleanup, безопасное окружение без window.
- Интеграционные тесты сохранения draft/query/selection при resize и переходах; отправка не дублируется.
- Доказательство, что responsive CSS и выбор альтернативного представления используют одинаковую границу.
- Проверка focus-переходов и закрытия wide-настроек через Escape.
- Отдельная проверка: изменяемые `ChatScreen`, `Rail`, `RoomList`, `ChatView`, `SettingsPanel` в `apps/web` не содержат оформительских HTML, `className` и `style`. Если имеющегося lint-правила нет, исполнитель выбирает минимальную проверку, не расширяя это в отдельный проект ESLint.
- Перед PR: `npx nx run-many -t typecheck,lint,test,build` успешно локально, поскольку CI ещё не настроена.

### Storybook и browser-проверка

Полноэкранные истории каркаса: комнаты, открытая переписка, настройки, отсутствие выбора, длинный контент. Размеры: 320, 390, 767, 768, 1024 и 1440 CSS px; короткая landscape-высота; light/dark и RU/EN. Проверяется повторный resize без reload, focus и отсутствие доступных скрытых контролов.

jsdom не доказывает CSS-раскладку: браузерная проверка обязана подтвердить отсутствие page horizontal overflow, внутреннюю прокрутку и видимость нижних действий. На compact выбранная переписка занимает всю ширину; в точке 768 px нет промежуточной или смешанной раскладки. При 200% zoom интерфейс продолжает reflow.

Клавиатура и реальные safe-area требуют отдельной проверки в мобильных браузерах iOS Safari/Android Chrome, если устройства доступны. При их отсутствии отчёт явно разделяет подтверждённое desktop/emulation поведение и непроверенные физические устройства; эмуляция не выдаётся за такую проверку.

### Документация

Обновить `ARCHITECTURE.md` и `libs/ui/README.md`: режимы, подключение shared styles, семантические слоты, хранение состояния над заменяемым UI, правила выбора CSS/container adaptation против замены представления, примеры нового адаптивного компонента и команды Storybook/проверок.

## 11. Решения, оставленные исполнителю

Точные размеры, имена компонентов/props, механизм общего breakpoint-источника и подписки, подходящий доступный overlay без обязательной новой зависимости, детали focus/ref API и визуальные нюансы в рамках темы. Нельзя самостоятельно добавлять разделы, менять правила переходов, заводить отдельную mobile-бизнес-логику или убирать возможность замены компонентов.
